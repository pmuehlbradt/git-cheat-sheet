↗ GIT / THE BASICS

Where do your changes go?

Git takes your work from a file on your computer to a shared project history. Here’s how the pieces connect—and what each command actually does.

What happens at each step

A closer look
01

Select your changes

git add
Working directory→Staging

Run git add to select a file’s current contents for your next commit. Your file stays where it is; Git keeps a separate copy of the contents you selected.

Edit it again? Run git add again to include the newer changes.

git add index.html

Check your selection with git diff --staged.

02

Save a checkpoint

git commit
Staging→Local repo

Record your staged changes as a commit on the current branch. The message explains what changed, and the commit becomes part of your local history.

Only staged changes are included. Your commit stays on your computer until you push.

git commit -m "Add page layout"

See your checkpoints with git log --oneline.

03

Share your commits

git push
Local repo→Remote repo

Send your local commits to a branch on the remote. Your teammates can now fetch them, and you can open a pull request if your project uses reviews.

Push sends commits. Uncommitted file changes stay on your computer.

git push -u origin main

First push: set the upstream with -u. After that, use git push.

04

Bring changes back

git pull
Remote repo→Local repo

Fetch remote commits and integrate them into your current branch, updating your working files. This keeps your local work in sync with the team.

--ff-only stops if the branches have diverged, so you can decide how to reconcile them.

git pull --ff-only

Commit or stash your unfinished changes before pulling.

Get started

Clone a project

git clone

Get a project that already exists on a server. Clone creates a new folder containing its history and a working copy of its files.

git clone https://github.com/example/project.git
cd project

Replace the example URL with your repository URL.

Remote repo→Local repo→Working files

What happens: Git downloads the history, creates a remote called origin, and checks out the default branch. The checked-out files are already tracked.

Clone once to get started. Use pull to update the same clone later.

Start from scratch

Initialize a repository

git init

Have a folder with no Git history? Initialize it, then select and commit the files you want to track.

git init -b main
git add index.html
git commit -m "Initial commit"

Run these commands inside your project folder.

Project folder→Empty repository→First commit

What happens: init creates the .git directory. Adding and committing creates your first saved snapshot. A remote is not created automatically.

To connect an existing empty remote: git remote add origin <repository-url>, then git push -u origin main.

Work in parallel

Create & switch branches

git branch / git switch

A branch is a name pointing to a commit. Create a branch for a feature, commit your work there, and switch back when you need another line of development.

git branch
git switch -c feature/header
# After committing your work:
git switch main

git branch lists local branches; * marks the current branch.

main · A→feature/header · A → B→main · A

What happens: The feature branch starts at your current commit. New commits advance that branch. Switching back restores main’s files and changes where the next commit will go.

git branch feature/header creates without switching. Commit or stash unfinished changes before switching if they would conflict.

Check your bearings

Inspect the working state

git status

See your branch, staged changes, unstaged changes, and untracked files before you decide what to do next.

git status
git status --short

The short format uses two columns to summarize file changes.

Working files + staging→Status report

What happens: Git reads your current state. In short output, the first column describes staging, the second describes the working tree, and ?? means untracked.

Read-only: your files, staging area, and commit history stay unchanged.

Review before saving

Compare your changes

git diff

See the lines added and removed. Pick a comparison for unstaged edits, staged edits, or work on a feature branch.

git diff
git diff --staged
git diff main...feature/header

In the output, + marks added lines and - marks removed lines.

Two versions→Line-by-line comparison

What happens: git diff compares working files with staging. --staged compares staging with HEAD. The branch example shows feature/header changes since its common ancestor with main.

Read-only. Untracked files do not appear in normal git diff output.

Explore the history

Browse saved commits

git log

See the saved checkpoints and how branches connect. Open a commit to inspect its message and patch.

git log --oneline --graph --decorate --all
git show HEAD

HEAD usually points to your current branch’s latest commit.

Saved commits→History & patches

What happens: Git reads commit history. --all includes local and remote-tracking references; git show HEAD displays the latest commit and its changes.

Read-only. Press q to leave the pager if one opens.

Adjust your selection

Remove a file from staging

git restore --staged

Staged a file too soon? Remove it from the next commit while keeping its edits on disk. You can add it again when you are ready.

git restore --staged index.html
git status

This command assumes the repository already has a commit.

Staged changes→Edits kept in working files

What happens: Git resets the file’s staged snapshot to HEAD without changing the working file. A newly added file becomes untracked again; edits to a tracked file become unstaged.

Before the first commit, use git rm --cached -- index.html to unstage a newly added file while keeping it on disk.

Finish the last checkpoint

Append to the latest commit

git commit --amend

Forgot a file or need to fix your last commit? Stage the extra changes and amend the latest commit.

git add index.html
git commit --amend --no-edit

Omit --no-edit to edit the commit message too.

Latest commit + staging→Replacement commit · new ID

What happens: Amending replaces the branch’s latest commit with a new commit that includes your staged changes. --no-edit keeps its message.

Use for local, unpushed commits. Amending published work rewrites shared history and requires coordination with your team.

Discard an unwanted edit

Discard edits

git restore

Undo edits you haven’t selected with git add. Git restores the file to the version selected for your next commit. If you haven’t staged any changes to this file, it restores the version from your latest commit.

git diff -- index.html
git restore -- index.html

Review with git diff first, then use git restore to discard those unstaged edits.

File with unstaged edits→File restored · unstaged edits removed

What happens: Only edits made since the file was last staged are discarded. If you never staged changes to this file, all edits since its latest commit are discarded. This does not stage anything or delete untracked files.

This discards edits that may have no saved copy. Stash them first if you might need them later.

Undo a saved change

Reverse a commit

git revert

Undo a saved change by adding a commit that reverses it. The original history remains, so this works for commits you have already shared.

git log --oneline
git revert HEAD

Replace HEAD with a commit ID to reverse a specific earlier commit.

A → B→A → B → revert B

What happens: Git applies inverse changes and records a new commit. The original stays in history. Push the new commit to share the undo.

Start with a clean working tree. For conflicts, resolve and stage the files, then git revert --continue. Use git revert --abort to cancel.

Inspect remote updates

Download without integrating

git fetch

Download new remote commits before deciding how to integrate them. Fetch lets you inspect what changed first.

git fetch origin
git log --oneline HEAD..origin/main

The log lists commits on origin/main not reachable from HEAD.

Remote repo→Remote-tracking refs · origin/main

What happens: Commits are downloaded and remote-tracking references update. Your current local branch, staged changes, and working files stay as they were.

Fetch downloads only. Pull fetches and then integrates into the current branch.

Bring work together

Merge a feature branch

git merge

When your feature is committed, switch to the branch that should receive it, then merge the feature branch.

git switch main
git merge feature/header

Start with a clean working tree: commit or stash unfinished changes.

main + feature/header→Updated main

What happens: Git advances main directly when possible (a fast-forward), or creates a merge commit joining both histories. Working files update to the merged result.

For conflicts, edit the marked files, git add the resolved files, then git commit. Use git merge --abort to cancel an in-progress merge.

Pause unfinished work

Save changes for later

git stash

Temporarily set aside unfinished tracked changes, switch tasks, then restore them when you return to the original branch.

git stash push -m "Header in progress"
# Back on your original branch later:
git stash apply
# Check the restored work, then:
git stash drop

git stash list shows entries. Add -u to push to include untracked files.

Uncommitted changes→Local stash→Working files again

What happens: Stash stores tracked staged and unstaged changes locally and resets them from the working state. apply restores changes and retains the entry; drop removes the latest entry.

Applying can cause conflicts. Check your restored work before dropping the entry. Use apply --index to also restore its staged state.

ⓘ

Not sure where you are? Run git status. It shows your branch, staged changes, modified files, and untracked files.
